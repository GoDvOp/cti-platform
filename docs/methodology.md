# Методика стажёра аналитика

Исследовательский вопрос: какие организации в фиксированной выборке требуют первоочередной ручной проверки по открытым признакам интереса атакующих? Результат — очередь проверки и, при достаточных основаниях, экспертный индекс. Это не вероятность атаки и не оценка безопасности компании.

## Границы

Начальная выборка: Аэрофлот, Novabev Group, ВинЛаб, Ростелеком, Яндекс. Группа и бренд учитываются раздельно; их упоминания могут относиться к одному событию. Начальный рабочий период — последние 90 дней на дату расчёта; для исторического кейса 2025 года применяется отдельная пометка. Прогнозный горизонт для будущей проверки качества — 30 дней. Исторический кейс не выдаётся за текущий сигнал.

Автоматические типы: заявление о продаже доступа, утечке, вымогательстве, нарушении доступности, атаке; уязвимости — отдельный контекст. Классификатор выбирает один тип по приоритету правил, а не извлекает все возможные типы. Мотив и атрибуция автоматически не устанавливаются.

## Работа аналитика

1. Зафиксировать список компаний, алиасов, период и фактически доступные источники. Пробный набор не должен строиться исключительно из будущих известных жертв.
2. Получить публикации из разрешённых feeds или импортировать минимальные открытые выдержки. Для каждого материала сохранить происхождение и отдельные времена публикации/сбора. Дата события фиксируется в примечании, если доказана; отдельной автоматически заполненной event_date в MVP нет.
3. Рассмотреть кандидата: совпадает ли компания, не указан ли чужой похожий домен, нет ли одноимённого юрлица? Анонимное объявление нельзя приписывать компании по отрасли.
4. Разделить наблюдаемый факт публикации, слова автора и собственный вывод. Проверить отрицания, старые объявления, перепечатки и альтернативы. Опровержение не превращается в подтверждение утечки из-за ключевого слова.
5. Поставить отдельный статус сопоставления компании и конкретного заявления, указать проверяющего и основания. Подтверждение факта атаки не подтверждает автора, точный масштаб утечки или работоспособность продаваемого доступа.
6. Передать старшему аналитику адресный сигнал о доступе или вымогательстве по конкретной компании вне очереди. Правило применяется после проверки сопоставления; итоговый балл не должен задерживать триаж. Программа показывает кандидатов и не отправляет уведомления автоматически.
7. Заполнить факторы только при наличии доказательств. Экспортировать карточки с неизвестными параметрами и следующим действием.

## Объединение сведений

У компании устойчивый ID, имя, алиасы и домены. У публикации ID определяется источником и GUID либо canonical URL. Повторный импорт идемпотентен. Копии сохраняются раздельно; одинаковый хеш нормализованных заголовка и текста отмечает точный кластер. Похожие тексты и общий инцидент автоматически не сливаются.

Новый текст по прежнему ID сбрасывает активную проверку; старые версии и проверки остаются в SQLite. Факторы привязаны к хешам проверенных публикаций: изменённое доказательство нельзя молча использовать. Схема позволяет отследить путь «компания → сигнал → публикация → версия → проверка».

## Факторы

| Фактор | Вес | Начальная шкала |
|---|---|---|
| I: адресный интерес | 50% | 0 — в явно проверенном охвате нет; 25 — косвенный сигнал; 50 — адресное неоднозначное заявление; 75 — конкретное заявление с проверяемыми деталями; 100 — несколько независимых адресных сигналов |
| S: отраслевой контекст | 30% | 0 — не выявлен в проверенной выборке; 25 — единичное наблюдение; 50 — повторения; 75 — несколько независимых событий; 100 — устойчивый профиль в нескольких сопоставимых периодах |
| H: сходство с другими целями | 20% | Выбрать географию и бизнес-модель как два признака: 0 — ни одного совпадения, 50 — одно, 100 — оба. Отрасль повторно не учитывается |

Это экспертные ориентиры, не обученная модель. Численные пороги отраслевой шкалы нужно зафиксировать в протоколе конкретного исследования до расчёта. Код не извлекает и не назначает S/H автоматически. Профиль строится по другим компаниям; текущую компанию нужно исключить. Дубли и материалы одного происхождения не дают дополнительных подтверждений. I оценивается по наиболее существенному независимому сигналу, а не сумме перепечаток.

Каждая ручная оценка содержит балл, обоснование, автора, дату наблюдения, уверенность, ID и хеши публикаций. Положительный I требует хотя бы одного проверенного сопоставления компании и не опровергнутого заявления. Нулевой I требует search_scope с источниками, интервалом и результатом проверки. Значимость бизнеса и CVSS в T не включаются.

Для каждого фактора: x = b × 2^(−t/90), где b — исходный балл, t — возраст наблюдения в днях. Затем T = 0,50I + 0,30S + 0,20H. Для нескольких оснований аналитик указывает дату наиболее существенного наблюдения, а не дату свежей перепечатки. Если время нельзя обосновать, фактор остаётся неизвестным. Период полураспада 90 дней — гипотеза; параметр --half-life позволяет проверить 30 и 180 дней.

Coverage — сумма весов доступных факторов. Пропуск не равен нулю. В реализации основной T появляется только при наличии всех трёх факторов. Частичный индекс рассчитывается по доступным весам, но не ранжируется: разные наборы факторов несопоставимы. Это более консервативное правило, чем предварительное предложение ранжировать при 80% покрытия.

Порог T ≥ 65 даёт категорию «приоритетная проверка», ниже — «наблюдение». Это временная UI-категория без доказанной прогностической эффективности. Уверенность low/medium/high задаётся по конкретным факторам; итог равен минимальной из них. Полное покрытие не означает высокую достоверность.

## Временные срезы и проверка качества

--as-of исключает будущие публикации, сбор и оценки. Архивы хранятся, но автоматическая реконструкция всех прошлых версий не реализована. Для воспроизводимого исторического эксперимента нужны отдельная замороженная БД и версии конфигурации. Полезные результаты модели нельзя подтверждать данными, собранными позже выбранной даты, без явного режима реконструкции.

На размеченных данных отдельно измеряются точность компании, тип события и дубли. Прошедшие unit-тесты не заменяют Precision/Recall на реальной выборке. Для прогноза заранее определить наблюдаемый исход, сравнить топ-K с простым отраслевым рейтингом на той же выборке, учесть неполноту публичных сообщений. Такой эксперимент пока не выполнен.
