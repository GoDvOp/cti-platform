# Методика weighted-graph-v2

Два экспертных индекса 0–100 характеризуют силу имеющихся оснований: интерес атакующих и технический контекст подверженности. Они не являются вероятностями атаки и не прошли калибровку. Отсутствующий путь даёт null, а не нулевой риск. Исследуемая выборка не обеспечивает одинакового покрытия всех компаний.

## Коэффициенты и даты

Конфигурация `config/graph_weights.json` проверяется перед расчётом. Её SHA-256 и версия сохраняются в каждом результате. high=1, medium=0,7, low=0,4 — экспертные коэффициенты, не вероятности истинности. При отсутствии явной уверенности используется medium. Тип основания задаёт второй коэффициент: сообщение потерпевшей стороны 0,9, исследование 0,85, бюллетень разработчика/государственного органа 0,9, обвинение 0,65, заявление атакующего 0,3, неуточнённое основание 0,6.

Вес = качество × временной множитель. Качество = уверенность × коэффициент основания. Для адресного сигнала вместо основания используется статус проверки: unresolved=0,4, corroborated=0,7, confirmed=1. Сопоставление компании должно быть подтверждено; непроверенный или опровергнутый сигнал не повышает оценку.

| Тип связи | Политика даты |
|---|---|
| Использование ПО, сигналы, история инцидентов | Затухание 2 ** (−возраст / период). Для интереса 90 дней, технического использования 180 |
| CVE затрагивает диапазон продукта | Статический проверенный факт, без временного затухания |
| Подтверждённое источником использование CVE группой или в инциденте; запись KEV | Статический факт известной эксплуатации, без вывода о текущем интересе к компании |
| Отрасль включает компанию | Структура каталога, самостоятельного доказательного веса нет |

Неизвестная дата статического бюллетеня сохраняется неизвестной. Она не превращается в сегодняшнюю; проверенные применимость и диапазоны не исчезают из-за отсутствия даты публикации. Неизвестная дата использования ПО блокирует такой путь. Изменившийся текст требует повторной проверки. Будущие даты, загрузки и проверки после as_of исключаются. Совпадение CVE и продукта в одном заголовке само не считается подтверждённой связью.

В режиме v2 старый бюллетень не делает свежую подтверждённую установку старой. Давнее использование ПО всё равно не доказывает текущую установку: оно затухает и отмечается как историческое основание. Сравнение v1.1/v2 на одних данных — `docs/analysis/model_comparison.json`; это исправление смысла связей, не подгонка весов под желательные ответы.

## Индекс интереса

Бюджеты компонентов: адресные сигналы 60, история инцидентов 20, отраслевой контекст 20. Вклад пути = бюджет × минимальный вес звена. Внутри компонента берётся максимум. Слагаемые по убыванию вклада проходят проверку общих событий. Один известный инцидент не заполняет два компонента; своя кампания исключается из отраслевого контекста.

Объединение событий использует ID инцидента, подтверждённые incident_part_of, URL, хеши и metadata.incident_id. Перепечатки не повышают оценку. Разные тексты об одном событии могут потребовать ручного объединения; смысловая дедупликация не решена полностью. Максимум компонента ограничивает ошибку, но не заменяет проверку.

Публикации с signal_scope=historical_incident/recovery_update/business_followup не являются новыми адресными сигналами. Свежая статья о последствиях старой атаки не делает её новой. Справочник MITRE, совпадение ПО и наличие CVE не добавляют интерес сами по себе.

## Технический индекс

Путь требует проверенного использования ПО и проверенной связи CVE с продуктом. Совпадение точной версии с диапазоном даёт множитель 1, неизвестная версия/неполный диапазон — 0,25. Версия вне диапазона исключает путь. Конфигурация, внешняя доступность и компенсирующие меры отдельно не проверены.

Базовый контекст = 0,6. При подтверждённом actor_exploits, incident_exploited или KEV контекст = 0,6 + 0,4 × вес дополнительного основания. Оно также участвует в проверке минимального веса. Прибавка относится к тому же пути, не к независимой второй оценке за ту же CVE. Из всех технических путей берётся один максимум:

```text
100 × минимальный вес звена × множитель версии × контекст эксплуатации
```

incident_exploited позволяет учитывать факт эксплуатации без придуманной связи «группировка → CVE». Атрибуция, которая относится только к этапу вымогательства, не доказывает первоначальную эксплуатацию. Отсутствие CVE в последней сотне KEV не доказывает отсутствие эксплуатации.

## Вывод и воспроизведение

В отчёте показываются исходные пути, источники, выдержки, даты, вес и причины исключения. `component_coverage` показывает наличие компонентов, не полноту мониторинга. Положительные баллы меньше 0,001 в HTML отображаются как «<0,001». Если ограничивающие временные звенья старше трёх периодов полураспада, вывод помечен historical_evidence_only.

`graph-scores --company ID --explain` раскрывает расчёт; `--include-historical` добавляет зарубежные исторические кейсы. `--as-of` задаёт дату вычисления на текущем снимке, но не восстанавливает прежние тексты и проверки. Для ретроспективной оценки прогноза нужны заранее сохранённые снимки, критерий исхода, горизонт и контроль покрытия.

`graph-sensitivity` проверяет 45 сценариев на копии БД. Бюджеты нормализуются, ограниченные качества обрезаются; фактические изменения записаны. Диапазоны не являются доверительными интервалами. Основной конфиг при проверке не изменяется. Пользовательский конфиг можно передать через `graph-scores --weights`; отчёт и Neo4j используют основной конфиг.

В Neo4j у компании есть interest_index, technical_exposure_index и graph_score_explanation_json. У доказательных связей — weight, weight_quality, weight_decay, weight_temporal_policy, причина исключения и хеш параметров. Наличие веса не превращает утверждение источника в установленный факт. Полный старый ручной I/S/H сохраняется отдельной командой targets; эти числа не смешиваются.
